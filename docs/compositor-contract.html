One shell, three compositors

The shell never speaks to Hyprland, niri or Wayfire itself. It reads one picture of the desktop and asks for a small set of actions through a contract. A backend for each compositor turns that into the compositor's own language, and says what else the compositor can do.

The contract

internal/compositor
Types and interfaces only. Imports no backend and no GTK.

Snapshot

Outputs, workspaces and windows, with what is focused. Ids are opaque strings that only the backend understands.

Backend

What every compositor must do: deliver snapshots, focus and close a window, go to a workspace, move a window there.

Capabilities

The optional parts, each with a state. The shell checks the state before it offers the feature.

one backend is live per session, chosen by the environment

Backends

One package each. All the compositor-specific code lives here.

internal/hypr

Request socket and event socket. Dispatchers, or Lua where Hyprland runs it.

internal/niri

JSON lines on $NIRI_SOCKET, one connection kept open as the event stream.

internal/wayfire

Plugin methods on $WAYFIRE_SOCKET. Displays are read through the wlroots output protocol.

Compositors

Versions the shell was run on.

Hyprland

0.57. The default, and the only one with every feature.

niri

26.04. Scrolling columns, workspaces per display.

Wayfire

0.11 and 0.9 (Debian 13). Floating windows, a 3×3 workspace grid.

[State]what flows up

Every compositor is reduced to the same picture

Each backend listens to its compositor's events, reads the state again, and hands the shell a Snapshot only when it changed. The bar, the dock, the launcher and the overview all redraw from that one value. The ids inside it mean something different on each compositor, and the shell never looks inside them.

[Actions]what flows down

One request, three languages

Typing "move to workspace 3" in the launcher makes the same call on every compositor. The backend decides what that means.

comp.MoveWindow(ctx, window, workspace, follow)

Hyprland

movetoworkspace 3,address:0x55d2…

A dispatcher on the request socket, or the Lua form where Hyprland runs Lua.

niri

{"Action": {"MoveWindowToWorkspace":
  {"window_id": 10,
   "reference": {"Id": 2},
   "focus": true}}}

One JSON line; niri answers Handled.

Wayfire

vswitch/send-view {view-id: 3, x: 2, y: 0}
window-rules/focus-view {id: 3}

Two plugin methods. Wayfire 0.9 has no send-view, so there the backend moves the window by whole screens instead.

[Capabilities]what differs

The shell asks before it offers

Beyond the baseline, a compositor may or may not have a feature. The backend reports each one as supported, unavailable (it can be turned on: a plugin, a line in a config) or unsupported. The shell reads that state, so nothing is offered that would silently do nothing.

On Wayfire a "yes" holds while the plugin behind it is loaded. The backend asks Wayfire for its method list at each connection, so unloading a plugin turns the feature off in the shell, and loading it turns it back on.

What the user sees when a feature is missing

  • A settings option is disabled and dimmed, with the reason under it.
  • A launcher command that cannot work is not listed.
  • Where a second way exists, the shell takes it: a paste is typed into the focused window.

[Settings]the same values, written three ways

inua's settings go through the same layer

Keyboard options, touchpad speed, shortcuts and display rules are kept once, in config.toml. internal/compsettings turns them into a neutral Settings value, and each backend applies it in the way its compositor takes settings.

[Session]from the login screen to a live backend

How a backend gets chosen

  1. Settings → Compositor saves the choice as [session] compositor and writes that compositor's sample config if there is none.
  2. At login, inua-session asks inua session compositor which one to start. If the chosen one is not installed or its config would not start the shell, it starts Hyprland and keeps the reason for the shell to show.
  3. The compositor starts inua-shell from its own config: exec-once, spawn-at-startup or autostart.
  4. The shell calls compositor.Detect(). Each backend looks for its own variable (HYPRLAND_INSTANCE_SIGNATURE, NIRI_SOCKET, WAYFIRE_SOCKET); the one that finds it is the backend for this session.
  5. The backend connects, reports its capabilities, and sends the first snapshot. If the connection drops it reconnects and reports again.
[Extending]

Adding a compositor

  • Write a package that implements Backend and registers itself.
  • Add it to internal/compositors, which links the backends into each program.
  • Implement the optional interfaces the compositor can serve, and report their capabilities.
  • The shell needs no change: what the backend reports decides what appears.
[Limits]

Still Hyprland's own

  • Live window previews, which use Hyprland's own capture protocol.
  • The key observer behind Super tap and Super+Tab.
  • The virtual screen that Remote Desktop makes on a computer with no monitor.
  • Turning the laptop panel off when the lid closes.
